# Standalone GT06/W07C firmware review — 2026-11-08

Reviewed commit: `4581e788643e0a65856fdf8103098783f4f7fa22`. The requested source files matched this commit. All code references below link to that exact GitHub revision.

This was a local, read-only source review, with this report as the sole output file. No devices, remote services, or local test servers were contacted. I read the requested context documents and used `server/protocol_GT06.py` to check commands sent by the server. I compiled the ARM C sources to assembly on stdout using the production CPU/optimisation flags; no firmware artifacts were changed. I also checked resolver-slot coverage and calculated the small counterexamples noted below. I did **not** run the socket-based SITL suites or claim hardware validation.

**Assessment:** fix the watchdog's blocking USB output before relying on unattended recovery. FOTA protects against an interrupted download overwriting the running partition, but its current checks do not establish that an update is bootable, and its download loop can keep the app occupied for days. Ordinary idle turns GPS off; it does not by itself establish low modem current, and the optional sleep path does not operate when coverage is lost.

Severity: **P1** = potential persistent outage, loss of autonomous recovery, or nonbootable update; **P2** = significant recovery, race-data, or battery defect under a stated trigger; **P3** = diagnostic defect. A finding describes a code-level defect or missing safeguard; hardware-dependent consequences are identified explicitly.

## Findings, ranked by severity

### P1-01 — The watchdog can block in USB output before it reaches the reset

**Code:** [reliability.c:55–64](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L55-L64), [reliability.c:99–125](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L99-L125); blocking-write contract in [main.c:214–221](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L214-L221); shipping watchdog selection in [main.c:34–49](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L34-L49).

`wd_tick()` calls `wr_hex()` on every healthy tick, every stalled tick, and immediately before reset. `wr_hex()` calls the raw resident `WR()` synchronously from the resident timer thread. It bypasses the main app's VCOM backoff and `SZCS#VCOM=0`; its only suppression gate is forwarding being configured. The source explicitly documents that this writer can block when USB is enumerated without a reader or during enumeration transitions.

**Failure scenario:** a charger/no-reader or USB transition blocks a watchdog diagnostic. The callback cannot return or reach `soc_reset()`. `g_uptime` also stops advancing, freezing reconnect, heartbeat, GPS-retry and recovery deadlines. The only watchdog enabled by this build is now blocked; the hardware watchdog is disabled. Depending on resident timer-thread semantics, other timer-driven services can also be affected. This is a concrete route to a unit needing physical recovery, although the particular USB trigger must be reproduced on hardware.

**Suggested fix:** remove **all** blocking I/O from `wd_tick()`, including the final `WD:FIRE` print. Record counters/phase in RAM and let a task export them. Test watchdog reset with USB disconnected, a charger, an enumerated unread port, and an actively read port. `VCOM=0` alone does not fix this path.

### P1-02 — Startup hangs and timer-creation failure have no effective watchdog

**Code:** [main.c:3231–3250](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3231-L3250), [main.c:3312–3317](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3312-L3317), [main.c:3385–3412](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3385-L3412); [reliability.c:107–110](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L107-L110), [reliability.c:140–171](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L140-L171).

Filesystem loads, boot USB output, `NetworkInit` and network-status startup run before the watchdog timer is created. After creation, the callback waits indefinitely for the **first** `wd_alive()` before counting stalls. In production that feed occurs only on entering the main loop, after queue creation/attachment, config reads, IMEI lookup, GPS power-off and battery initialisation. A hang in any of those calls escapes protection. Separately, timer-create failure is logged but execution continues; `g_uptime` then remains zero and there is no watchdog or advancing recovery clock.

**Failure scenario:** a resident service blocks during boot, or timer allocation fails. The app never reaches useful tracking/recovery, and the software watchdog never expires. If the main loop runs with no timer, it can make an initial connection attempt but its normal timed work cannot progress.

**Suggested fix:** start checked watchdog/timebase infrastructure as early as feasible, give startup a finite deadline independent of the first feed, and treat timer-start/creation failure as a controlled recovery condition. Add startup phases. Do not enable the known-problematic CP watchdog merely to fill this gap.

### P1-03 — A matching compressed-body CRC is treated as sufficient evidence to commit firmware

**Code:** [main.c:2750–2786](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2750-L2786), [main.c:2787–2797](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2787-L2797); resident API contract in [sapi.h:231–245](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sapi.h#L231-L245).

The pre-close gate checks compressed byte count and CRC. It does not check the LZMA header, decompressed size, app descriptor/entry point, target compatibility, or an approved image identity. The resident verifier's documented contract is also header/CRC validation. Thus the app can set the pending marker for content whose bytes transferred correctly but which is not a usable application. The compressed-size cap is not a bound on decompressed memory use.

**Concrete counterexample:** a wrapper with `clen=1`, payload ASCII `x`, and stored CRC `0x7323e97c` passes the app's pre-close predicate (`total=9`); that payload is not LZMA. A correctly packaged image for the wrong application is a more realistic operator-error case. Whether the resident loader rejects a malformed stream without damaging the usable app is **not established by these sources**; this review does not claim a hardware-proven brick from the one-byte example. There is no app-level rollback safeguard here.

`fcls()` also sets the pending marker **before** `fver()`. A verification failure leaves that marker set while normal operation resumes. The comment relies on boot-time CRC rejection; the app has no explicit abort/marker-clear path, so “staying on current app” is not a complete update cancellation.

**Suggested fix:** validate the approved image and its decompressed size/descriptor before making it pending; use an authenticated manifest or pinned expected image hash where practical. Make post-close failure explicitly cancel the pending update, or prove the resident rejection/rollback behavior for each failure class. Keep power-interruption safety separate from bootability/rollback claims.

### P1-04 — FOTA can keep feeding the watchdog while stranding the tracker in the downloader

**Code:** [main.c:2682–2735](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2682-L2735), [main.c:2747–2769](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2747-L2769), invocation at [main.c:3440–3442](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3440-L3442).

The download loop has a byte cap and a count of consecutive negative receives, but no overall elapsed-time deadline or minimum sustained progress. Every positive receive resets `idle`, and every iteration feeds the watchdog. The main loop does no command handling, GPS capture, SOS processing or tracking reconnect while this function runs.

**Failure scenario:** an HTTP endpoint delivers one byte every 30 seconds, with timeout returns between bytes. With the source's approximately five-second receive timeout, this stays below the 13-negative-receive abort threshold. The function feeds the watchdog throughout. Even a 65,536-byte image can then take about 22.8 days; the whole-response byte ceiling permits still longer occupation. This is a live app making insufficient useful progress, so the liveness watchdog cannot rescue it.

There are also no feeds/deadline handling around preparation, blocking `connect()`, request transmission, flash open/write/close or final verification. A single such call exceeding the watchdog window can instead reset an otherwise legitimate update. The nonblocking main reconnect implementation is not used for the FOTA connection.

**Suggested fix:** impose an absolute update deadline and a progress deadline; use bounded/polled connection and transfer states. Only feed while the update state meets those deadlines. Abort safely before making an image pending, and return to service or perform one controlled reset with a recorded reason.

### P2-01 — The default PLMN policy bypasses the CFUN/COPS recovery ladder entirely

**Code:** default list [main.c:1172–1178](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1172-L1178); restricted policy [main.c:2412–2492](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2412-L2492); early return [main.c:2509–2516](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2509-L2516); bypassed ladder [main.c:2534–2577](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2534-L2577).

With the shipping nonempty `50501,50502` list, `plmn_policy()` always returns 1. `cell_recovery()` then clears its ladder state and returns before **any** CFUN cycle, COPS deregister/automatic reselection, or scan rung. Restricted recovery only retries manual selection of the configured operators, with 120-second settle intervals and a one-hour pause after a failed round. `at_cmd()` discards the resident send return value ([main.c:1079–1084](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1079-L1084)), so an attempted manual selection counts even if command submission fails.

**Failure scenario:** the modem/control path requires the CFUN reset that the legacy ladder was written to provide, but repeated manual COPS commands cannot recover it. The main loop continues feeding, so no watchdog fires; the unit repeats the restricted attempts indefinitely. This does not mean ordinary carrier denial necessarily fails: trying another allowed carrier can recover that case. It means the documented full ladder is unavailable with the default policy.

**Suggested fix:** retain the whitelist while adding bounded CFUN/control-path recovery after unsuccessful permitted-operator rounds; check command submission/completion. Keep the backoff and avoid unrestricted `COPS=0` if that violates the configured policy. Test radio/control failures separately from normal denied registration.

### P2-02 — Config corruption can strand the unit despite a usable backup

**Code:** boot load [main.c:3323–3354](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3323-L3354); safer but separate command-time validation [main.c:1817–1832](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1817-L1832); writes [main.c:1834–1848](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1834-L1848); production fallback [main.c:3350–3365](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3350-L3365).

Boot tries `cwbank.bin` only when opening `cwprm.bin` fails. An openable but short/corrupt primary wins over a good backup. It ignores the read length and validates only the **first** TERIID character, then copies all 15 bytes and trusts the stored port. `parse_ip()` can partly modify the destination before failing, and this return is ignored. An unreadable config also falls back to **8711**, the test port, rather than the documented production port 7711.

Writes truncate the primary in place, ignore close errors and update the backup even when the primary write failed. Consequently a failed/short primary write can be followed by a complete backup write that boot never tries.

**Failure scenario:** power loss or a write failure leaves an openable truncated primary. On reboot the unit selects corrupt identity/address/port values instead of the good backup, or falls onto the test port. The link needed to repair settings remotely may never be established.

**Suggested fix:** validate full length, all identity digits, bounded IP and a valid port before selecting either copy; try the backup on **validation failure**. Parse into temporary values. Use a verified, crash-consistent save strategy and honor close errors; choose an intentional production recovery endpoint. The alternating checksummed PLMN records already provide a better local pattern ([main.c:1210–1262](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1210-L1262)).

### P2-03 — Main-loop USB and socket operations still have no bounded blocking budget

**Code:** USB “guard” [main.c:292–304](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L292-L304); restore blocking mode/login [main.c:3544–3549](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3544-L3549); sends [main.c:3651–3659](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3651-L3659), [main.c:3681–3686](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3681-L3686), [main.c:382–383](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L382-L383); tracing-only wrapper [main.c:2803–2810](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2803-L2810).

`vcom_write_guarded()` measures elapsed time **after** `WR()` returns. It cannot interrupt the first blocking write. Likewise, GT06 sockets are restored to blocking mode; `send_traced()` records a phase but adds no deadline or feed. Multiple replay sends can occur in one main-loop iteration, sharing one watchdog budget. These are distinct from the normally nonblocking connection-establishment path.

**Failure scenario:** a full socket send buffer during coverage loss, or an unread USB endpoint, holds a call beyond approximately 12 seconds. If the watchdog remains functional, it resets the whole tracker and loses its RAM backlog; if P1-01 also triggers, recovery can be lost. Repeating the same environmental condition after boot can repeat the reset. The source proves the missing bound, not a specific resident send timeout.

**Suggested fix:** give data-path operations a tested bounded deadline/backpressure strategy and budget the whole iteration, including replay. Make optional debug output drop rather than block. Do not simply add unconditional feeds around an indefinitely blocked call.

### P2-04 — A silent/wedged GNSS receiver has no escalation beyond repeating ON/configure

**Code:** [main.c:1004–1065](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1004-L1065), [main.c:3617–3641](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3617-L3641); NMEA health counters [main.c:2183–2217](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2183-L2217).

Tracking repeats `power(1)` plus NMEA configuration every ten seconds regardless of health. A receiver already reported ON commonly returns -1; this leads directly to reasserting configuration. There is no stale-NMEA deadline that cycles OFF/ON, no GNSS recovery ladder and no eventual controlled reboot. The code comment itself describes a receiver that previously needed a full reset. The server's WSTR setting whitelist intentionally omits `GPS_RST_TIME` ([protocol_GT06.py:213–222](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/server/protocol_GT06.py#L213-L222)), so that vendor feature is not a fallback.

**Failure scenario:** GNSS reports ON but stops emitting sentences and ignores repeated configuration. TCP/heartbeats remain healthy forever, but no race positions arrive. The main-loop watchdog sees progress and does nothing.

**Suggested fix:** use NMEA age, separately from valid-fix age, to trigger bounded recovery: reconfigure, power-cycle with settle time, then a rate-limited full restart if necessary. A healthy receiver reporting void fixes indoors must be distinguished from a silent service. Expose recovery counts remotely.

### P2-05 — Night sleep stops working precisely when the unit loses server connectivity

**Code:** sleep gate [main.c:3466–3473](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3466-L3473); reconnect [main.c:3509–3525](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3509-L3525); policy/backoff [main.c:2446–2490](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2446-L2490).

Disconnected sleep requires `connected`. If the server/radio is unreachable after a scheduled wake, the unit stays in the ordinary reconnect loop instead of returning to bounded idle sleep. Fast failures permit connection attempts about every five seconds; pending attempts last up to 30 seconds. Radio selection can also continue under the PLMN policy. Its one-hour operator holdoff does **not** suppress socket retries. The sleep flag is RAM-only and defaults to zero, so a reboot while offline loses that night policy altogether ([main.c:1407–1416](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1407-L1416), [main.c:2040–2048](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2040-L2048)).

**Failure scenario:** an idle tracker loses coverage overnight, or a no-SIM unit boots. GPS can be correctly off while modem searching and repeated connection/control work consume the battery. The high-current condition can last all night because there is no successful login to satisfy the sleep precondition.

**Suggested fix:** add a locally enforceable idle/no-coverage backoff and timed sleep path independent of successful TCP establishment, with bounded check-ins and explicit SOS handling. Preserve enough safe night policy across a reboot if overnight behavior must survive outages.

### P2-06 — Deliberate night sleep suspends SOS processing and disables watchdog protection through wake cleanup

**Code:** sleep interval and watchdog sequencing [main.c:3471–3498](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3471-L3498); SOS polling/parsing [main.c:3422–3438](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3422-L3438), [main.c:1487–1496](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1487-L1496); alarm sending [main.c:3690–3699](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3690-L3699).

The app parks on its private empty sleep queue for the selected interval plus one second, with the software watchdog disarmed. It does not poll/parse the supervisor button or send SOS during that wait. The existing `!g_sos_active` check only protects an alarm already latched **before** sleep. A new press can therefore wait until the next check-in; a short press may be missed if the supervisor does not retain/report it. The possible delay is up to the one-hour heartbeat ceiling. These sources do not establish an independent M0 SOS wake/latch mechanism.

On wake, `set_sleep(0)` is called **before** `wd_alive(); wd_arm(1)`. A hang in that resident call leaves protection disabled indefinitely.

**Suggested fix:** define and verify SOS behavior during night sleep; use an actual button/event wake path or a bounded safety polling interval if alarms must remain available. Rearm protection before potentially blocking wake cleanup, with an explicit recovery deadline. Verify that a wake-disable failure really leaves the modem controllable.

### P2-07 — Receive/select errors do not move the GT06 state machine back to reconnect

**Code:** [main.c:3567–3585](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3567-L3585), idle wait [main.c:3724–3732](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3724-L3732); unchecked response sends [main.c:2615–2624](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2615-L2624).

The receive path handles EOF and positive data, but ignores negative `recv()` results. Negative `select()` results are also ignored, including the select used to pace the idle loop. Command-response sends ignore failed/short writes, unlike heartbeat/LOC sends.

**Failure scenario:** a socket left in a persistent error condition remains `connected` until some later send notices. If select repeatedly fails immediately, idle pacing disappears and the loop can spin, repeatedly feeding the watchdog. A broken inbound path can also prevent new TIMER/RESET/config commands without any receive-health deadline. Short command replies can damage framing on an otherwise retained TCP session.

**Suggested fix:** classify real errors versus transient timeout/would-block returns using the resident contract, close/reconnect on terminal errors, and retain a bounded delay on error paths. Check full command-response sends; maintain an application receive/ACK deadline rather than equating “login bytes accepted by send” with a healthy session.

### P2-08 — Server commands are executed without verifying their GT06 CRC or exact command shape

**Code:** frame extraction/dispatch [main.c:2585–2624](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2585-L2624); TIMER/HBT parsing [main.c:2625–2660](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2625-L2660); reset matching [main.c:2646–2649](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2646-L2649); FOTA parse [main.c:1799–1806](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1799-L1806).

The parser checks start bytes, length availability and CRLF, but never verifies the two CRC bytes. It also accepts prefix forms: `RESETjunk` requests a reset, and numeric parsing often accepts trailing junk or truncated values. A malformed TIMER still receives an OK reply before validation; generic SZCS/CXCS prefixes are considered recognized ([main.c:1633–1640](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1633-L1640)).

**Failure scenario:** a malformed command frame with a bad CRC but an apparent `RESET` or settings payload is acted upon. A framing/content error can therefore reboot a unit or change its persistent endpoint rather than being rejected. TCP's transport checksum does not replace validating the application's own frame contract.

**Suggested fix:** require a valid minimum frame length, exact content-length consistency and GT06 CRC before dispatch. Validate the complete command and arguments before replying OK or applying side effects; reject overlong/truncated commands instead of acting on their prefix. The current caller's 256-byte reads into a 768-byte accumulator do bound the append; I did not find a reachable accumulator overflow in this call path.

### P2-09 — A bounded blind replay does not guarantee that old fixes precede live ones

**Code:** replay limit [main.c:834–844](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L834-L844); flush [main.c:3645–3664](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3645-L3664); legacy live/replay order [main.c:3799–3822](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3799-L3822).

A flush calls `blind_replay_batched()` once and then sends the live batch even if the blind ring still contains older entries. One call drains at most five frames of ten fixes, sometimes fewer because of span boundaries. The legacy path sends the current live fix **before** replaying old fixes.

**Failure scenario:** configure `LOCBATCH=1`, fill the 300-fix ring during an outage, then reconnect. The first RMC can replay 50 fixes; the next live flush replays at most another 50 and then sends its new fix while roughly 200 older fixes remain. Later replay sends those older timestamps after the newer position. Default batching also has this issue whenever a partial live batch flushes before the backlog has drained, or replay packs sparsely. This breaks the intended chronological catch-up contract.

**Suggested fix:** keep live fixes behind the backlog until it is empty, spilling them into the same ordered queue as necessary; apply the same rule to legacy mode. Test a full backlog with batch sizes 0, 1 and 5 and assert monotonically ordered transmitted fix times.

### P2-10 — Blind batching ignores the date when calculating fix offsets

**Code:** [main.c:798–818](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L798-L818), shared delta rule [main.c:678–689](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L678-L689).

Blind records retain a full date, but replay calculates offsets only from hour/minute/second and deciseconds. Small backward steps clamp to zero; a large backward step is assumed to be a single midnight crossing. The 120-second span check therefore cannot detect a gap of one or more whole days at a similar time of day.

**Failure scenario:** an offline unit has fixes from day 1, then no valid GPS for a day, and obtains another fix around the same UTC time on day 2 before reconnecting. A frame crossing that gap can encode day-2 12:00:01 as only **10 deciseconds** after day-1 12:00:00. The true difference is 864,010 deciseconds. The 300-entry limit bounds fix count, not fix age; a long GPS outage makes this reachable in a multi-day test.

**Suggested fix:** compute offsets from the full UTC date/time, and split frames at any backward or excessive elapsed-time discontinuity. Include a date-changing long-fix-gap case in addition to the ordinary midnight test.

### P3-01 — Reset-reason logging cannot identify the current watchdog/command/FOTA resets

**Code:** [reliability.c:148–161](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L148-L161), watchdog reset [reliability.c:121–125](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L121-L125), command reset [main.c:3452–3457](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3452-L3457), FOTA reset [main.c:2781–2795](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2781-L2795).

Boot writes `RR_POWERON`. The production watchdog calls `soc_reset()` directly without saving `RR_WATCHDOG`; RESET and FOTA also call the raw reset function. Thus these software resets can all appear as POWERON on the next boot. The reason reader additionally accepts a short `wdstat.bin` based only on magic, without checking read length or initializing the rest of the struct.

**Failure scenario:** the reported 18m23s reboot repeats, but the reset record incorrectly suggests an external power/brownout cause, or a truncated record yields meaningless reason/count values. This obstructs diagnosis; it is not itself proof of a reboot cause.

**Suggested fix:** persist intentional command/update reasons from main context, use a safe retained-memory/hardware mechanism for watchdog cause, and validate full record length/content. Do not add filesystem writes to the timer callback.

## Idle battery observations

1. **Normal GPS-off logic is present.** Boot requests OFF, TIMER transitions request the selected state, and idle retries an unconfirmed OFF every ten seconds. The status getter is consulted at most once per loop timestamp; if it later reports ON, confirmation clears and OFF is retried. No accelerometer/movement path in this app powers GPS on. Idle discards NMEA and never builds LOC. These are favorable properties, not evidence of measured off-state current. See [main.c:3385–3389](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3385-L3389), [main.c:3584–3588](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3584-L3588), [main.c:3628–3641](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3628-L3641), [main.c:976–1001](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L976-L1001), [main.c:3747–3750](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3747-L3750).

2. **The compatibility fallback can falsely “confirm OFF.”** If the status getter is absent/invalid, silence is treated as power-off evidence after a successful/ambiguous OFF request. However, `g_nmea_ts` is updated only inside the tracking-only parser: idle discards NMEA first. With no previous tracking timestamp, `!g_nmea_ts` can confirm OFF immediately; after earlier tracking it can confirm despite ignored idle NMEA. That can stop OFF retries while an unobservable receiver remains powered. The reviewed target has a resolver mapping for the getter, so this is a fallback-specific limitation, not evidence that the normal target currently leaves GPS on. Prefer UNKNOWN/retry to silence-based confirmation unless idle NMEA is actually monitored. See [main.c:1137–1155](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1137-L1155), [main.c:3747–3763](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3747-L3763), [sapi.h:113–115](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sapi.h#L113-L115).

3. **TIMER's 1800-second idle value is not the heartbeat interval.** Heartbeats use HBT's OFF value, default **15 seconds**: 240 transmissions/hour or 5,760/day before server changes. Ordinary idle also wakes the app about once a second on select, polls the supervisor/charger every five seconds, and polls operator status every 30 seconds. WD USB diagnostics run about once a second. Those wakes/calls can prevent or reduce useful sleep depending on resident power management. `cxzt` hardcodes `*H:15`, so verify the actual interval on the wire instead of trusting that text. See [main.c:1405–1416](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1405-L1416), [main.c:1743–1745](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1743-L1745), [main.c:2504–2511](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2504-L2511), [main.c:3422–3438](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3422-L3438), [main.c:3678–3687](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3678-L3687), [main.c:3724–3732](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3724-L3732).

4. **App permission for system sleep is explicit only in the optional night path.** It closes TCP, programs the alarm, grants sleep, then parks the app. Ordinary connected idle contains no equivalent sleep-enable call. The server can request this night behavior with SLPDISCONNECT and long HBT values ([protocol_GT06.py:1593–1609](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/server/protocol_GT06.py#L1593-L1609)). Measure whether the resident timer and other tasks still wake the module during the parked interval; API success is not proof of LTE/RF deep sleep. No PSM/eDRX configuration is made by these reviewed app paths. See [main.c:3461–3498](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3461-L3498).

5. **Out-of-coverage/no-SIM idle is a separate power mode that is currently unbounded by sleep.** GPS remains idle by default, but socket retries and manual operator attempts continue as described in P2-05. Do not infer good battery life from GPS OFF alone. Conversely, the one-hour PLMN holdoff does protect against a continuous stream of operator selections; preserve it in any recovery changes.

6. **Real queue waits differ from the SITL model by five times.** `wd_sleep()` explicitly converts milliseconds to five-millisecond RTOS ticks, but the main loop passes `1000` directly to `mqr()` when tracking or disconnected: on the documented resident this is approximately **five seconds**, not one. Forwarding's nominal 20-ms queue wait is about 100 ms. This increases no-NMEA command/recovery latency and consumes more of the 12-second watchdog budget; it is not itself a busy poll. Connected idle uses the one-second socket select. See [reliability.c:39–50](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L39-L50), [main.c:3710–3732](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3710-L3732), [sitl_hal.c:310–325](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L310-L325).

7. **Forwarding changes the idle power budget substantially if enabled.** It caps connected-idle waits at 20 ms, keeps a second socket, and can send UDP keepalives every three seconds; it also excludes night sleep. Confirm `FWDPORT=0` on race trackers before comparing idle drain. See [main.c:2817–2833](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2817-L2833), [main.c:3107–3120](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3107-L3120), [main.c:3466–3468](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3466-L3468), [main.c:3720–3728](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3720-L3728).

## Historical faults and the exact 18m23s cycle

- **The ~13.5-minute 1-Hz reboot is marked FIXED in the roadmap**, with a payload-leak explanation ([roadmap.md:184–198](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/roadmap.md#L184-L198)). The current loop has a shared cleanup label calling `urc_free()` after AT, idle and tracking processing ([main.c:3747–3750](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3747-L3750), [main.c:3832–3834](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3832-L3834)), using the resident free slot ([main.c:1158–1167](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1158-L1167)). I did not find the original missing-free path in this revision. Invalid-address payloads are deliberately not freed. This is not proof against a different resident allocation leak.

- **The corrupt LOC at ~20 seconds is also marked FIXED**, rather than still listed as an open fault ([roadmap.md:199–206](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/roadmap.md#L199-L206)). Periodic CSQ now uses the direct getter, recognized AT chunks skip NMEA assembly, complete lines require a checksum, and valid fixes pass a continuity gate ([main.c:1073–1090](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L1073-L1090), [main.c:3747–3771](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L3747-L3771), [main.c:474–489](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L474-L489)). These changes address the documented AT/NMEA splice. They do not make an 8-bit checksum collision impossible or validate every semantic coordinate/date value. No evidence here establishes that the old recurring corruption still exists.

- **18m23s = 1,103 seconds: no matching periodic app reset was found.** The software watchdog fires after roughly 12 stalled ticks, not 1,103 seconds of uptime. Production recovery gates are 300/120/3,600 seconds; socket retry/pending limits are 5/30 seconds. The default nonempty PLMN policy does not execute CFUN recovery. A 32-bit seconds counter wraps after about 49,710 days, so ordinary seconds wrap does not explain this multi-minute cycle. See [reliability.c:18–19](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L18-L19), [reliability.c:105–125](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/reliability.c#L105-L125), [main.c:930–931](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L930-L931), [main.c:2353–2356](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2353-L2356), [main.c:2513–2516](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2513-L2516).

  A repeatable late blocking call could still produce “time to reach call + watchdog timeout,” and resident/modem/M0 behavior is outside the app implementation. **There is insufficient evidence to assign this cycle to a particular call, heap leak, watchdog, or power supervisor.** Do not label it the historical tracking leak merely because it is periodic. P3-01 means POWERON logging cannot distinguish those possibilities.

## Callback stacks, resolver coverage, and limits of SITL evidence

- All **456** generated resolver pairs have unique destination slots, and every named `SLOT_*` address in `sapi.h` occurs in the pair list. This rules out a missing static map entry; it does not prove that every runtime resolver result is nonzero or that every resident ABI is correct. The two constant supplements remain resident-version-dependent ([sapi_pairs.h:463–468](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sapi_pairs.h#L463-L468)).

- With production ARM flags, compiler assembly reports a 1,600-byte main-function local frame, a 64-byte UART callback local frame, no local frame for the hardware USB RX callback, and a 48-byte `wr_hex` local frame; saved registers/outgoing arguments and resident callees add to these. The descriptor requests a 0x2800-byte main stack. USB receive buffers and LOC batch scratch are now static, and command scratch is sized more generously than the old overflow comments describe ([main.c:651–661](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L651-L661), [main.c:2605–2613](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2605-L2613), [main.c:2863–2877](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/main.c#L2863-L2877), [usb_debug.c:54–61](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/usb_debug.c#L54-L61)). I found no demonstrated current callback stack overflow. Resident callback-stack headroom through `UartRead`, VCOM write, free, and reset still needs measurement. P1-01 is a blocking-context defect regardless of stack size.

- `usb_debug.c` is a **separate replacement image**, not linked into the tracker build. Its RX callback enqueues into static buffers, while replies/API calls occur in main context ([usb_debug.c:116–131](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/usb_debug.c#L116-L131), [usb_debug.c:284–317](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/usb_debug.c#L284-L317)). The debug image intentionally has a busy loop and dangerous-call mode; do not attribute that loop or those commands to the race tracker. It has no tracker watchdog/sleep behavior.

- SITL replaces watchdog behavior with no-op functions and its own host clock ([sitl_hal.c:67–89](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L67-L89)), interprets queue timeouts as milliseconds instead of resident ticks ([sitl_hal.c:310–325](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L310-L325)), changes GNSS power synchronously ([sitl_hal.c:399–409](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L399-L409)), and only logs sleep/alarm permission rather than suspending modem/CPU power ([sitl_hal.c:794–818](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L794-L818)). Its URCs live in a fixed mmap ring rather than separately allocated resident payloads ([sitl_hal.c:267–300](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L267-L300)); the slot initializer contains no FREE_R installation ([sitl_hal.c:903–962](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L903-L962)). It therefore cannot detect a regression of the historical URC heap leak. FOTA reset renames a host file and re-execs the **existing host executable**, rather than booting the downloaded app ([sitl_hal.c:878–892](https://github.com/tridge/windsurfer-tracker/blob/4581e788643e0a65856fdf8103098783f4f7fa22/gt06/Firmware/standalone/sitl_hal.c#L878-L892)). A clean SITL FOTA run does not validate new-image bootability, watchdog coverage, or power savings.

## Measurements worth running during the multi-day test

These are proposed tests only; none were run against a device or server in this review.

| Test | Record and acceptance evidence |
|---|---|
| **48–72 h idle comparison** | Compare standalone/vendor units with comparable batteries, RF conditions and HBT policy. Log supply current with enough resolution to see wake pulses and integrate mAh/day. Separate USB disconnected, charge-only supply, enumerated unread port, and actively read debug port; USB logging can change both power and failure behavior. Record actual heartbeat/check-in spacing. |
| **GPS off throughout idle** | Test cold idle boot, tracking→idle, charging transitions, reboot and failed OFF requests. Capture resident power getter, NMEA activity and measured current; require receiver current to remain at the off baseline. Test getter-unavailable fallback separately. Movement while idle should not start GPS. |
| **Night sleep and wake** | Test several HBT intervals, repeated wake/reconcile/sleep cycles, and the morning tracking command. Record sleep current, timer-wake pulses, sleep API returns, reconnect latency and GPS power through wake. Inject alarm-enable, sleep-enable and wake-disable failures. Require bounded recovery and a deliberate SOS policy. |
| **No SIM / denied / no coverage / server unreachable** | Treat these as separate cases. Record operator attempts, connect attempts, registration, current and recovery latency for at least 24 h. Restore service and require autonomous return. Verify the one-hour operator pause does not hide ongoing five-second TCP retries. Test both default restricted PLMN policy and explicitly unrestricted policy. |
| **18m23s reproduction** | Timestamp reset-to-reset over several cycles; record exact firmware hash, SIM state, USB reader state, last progress phase, URC count, last operator command, resident free heap/largest block if safely available, and supply voltage/current at reset. Compare constant wall time versus constant message/allocation count. Confirm a full app/SoC restart rather than only USB/modem re-enumeration.
